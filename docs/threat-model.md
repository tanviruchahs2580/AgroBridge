# Threat model

Scope: the containers and data flows in `docs/architecture.md` — the static SPA on the Vercel edge,
the API function (Express modular monolith) on Vercel Functions, PostgreSQL on Neon, the
rate-limit store, provider adapters, and the Android WebView shell. Threats are enumerated with
STRIDE per container/flow; every control names its code location and, where one exists, the test
that pins it. Where no test exists this file says so rather than implying coverage.

Test paths below are relative to the repository root. No risk ranking is used beyond
"risk" (what the abuse achieves) and "residual" (what remains after the control).

## Container / flow inventory

| # | Container or flow | Trust boundary crossing |
|---|---|---|
| F1 | Browser or Android WebView → HTTPS API | Untrusted client input into the API pipeline |
| F2 | API → PostgreSQL (Neon) | Application queries against tenant data |
| F3 | API → provider APIs (OpenWeather, OpenAI-compatible, SSLCommerz, SMS, S3) | Outbound calls carrying user data or credentials |
| F4 | Gateway → `POST /api/v1/payments/webhook/sslcommerz` | Unauthenticated inbound webhook |
| F5 | SPA bundle served from the edge | Static content integrity and headers |
| F6 | Offline queue (localStorage) → API replay | Delayed, replayed, possibly stale writes |
| F7 | AI knowledge base → provider prompt → farmer-visible answer | Untrusted text into a model |

## Abuse cases

| ID | Abuse case | STRIDE | Flow | Risk | Existing control (evidence) | Test that pins it | Residual |
|---|---|---|---|---|---|---|---|
| AC-01 | Credential stuffing against `POST /auth/login` | Spoofing | F1 | Account takeover | Per-IP login limiter 20 per 15 min (`loginLimiter` + `LOGIN_RATE_LIMIT_MAX`, `apps/api/src/modules/auth/routes.ts`); bcrypt cost 12 (`COST`, `apps/api/src/modules/auth/bcryptPool.ts`); uniform 401 plus dummy-hash comparison to equalise timing (the login handler, same auth routes file) | `apps/api/tests/login-timing-equalisation.test.ts`; `apps/api/tests/auth-rate-limit-envelope.test.ts` | Limiter is per instance without `REDIS_URL` (`limiterStore` selection in `apps/api/src/app.ts`); production reports `limiterStore: "memory"` on `/ready` (the audit working tree `.audit/v2/BASELINE.md` is not in this repository — see `docs/STATUS.md` §Where the evidence lives) |
| AC-02 | Stolen refresh token replayed after rotation | Spoofing | F1 | Persistent session hijack | Tokens stored hashed (`sha256`, refresh-token creation in `apps/api/src/modules/auth/routes.ts`); rotation is a claim-atomic revoke, and a replay revokes the whole family (the refresh handler, same file); logout revokes the presented token (same file) | `apps/api/tests/auth-session-integrity.test.ts`; `apps/api/tests/security-matrix.test.ts` | Tokens live in `localStorage` by accepted ADR-0003, so script execution in the SPA origin is equivalent to token theft |
| AC-03 | OTP brute force or SMS pumping on the verification flow | Spoofing / DoS | F1 | Phone takeover, SMS cost abuse | OTP request limiter 5 per hour; verify limiter 20 per hour keyed by user (`otpLimiter`, `otpVerifyLimiter` in `apps/api/src/modules/auth/routes.ts`); challenge TTL 5 min, max 5 attempts, a new code invalidates the old (`OTP_TTL_MINUTES` / `OTP_MAX_ATTEMPTS`, same file) | `apps/api/tests/auth-session-integrity.test.ts` | `SMS_PROVIDER=sandbox` does not deliver in production (OD-15), so phone verification is not reachable for real users today |
| AC-04 | IDOR/BOLA: reading or mutating another user's order, booking, payment, notification, disease case, or advisory | Information disclosure / Elevation | F2 | Cross-user data access | Ownership is part of every lookup scope, and misses return 404 without an existence oracle (`orderReadScope` in `apps/api/src/modules/marketplace/routes.ts`; payment lookups in `apps/api/src/modules/payments/routes.ts`; advisory history in `apps/api/src/modules/aiagent/routes.ts`) | `apps/api/tests/cross-user-negative.test.ts`; `apps/api/tests/security-matrix.test.ts`; `apps/api/tests/farm-event-sync-scoping.test.ts` | New routes must keep the same scoping convention; there is no schema-level (RLS) backstop (OD-05) |
| AC-05 | Privilege escalation via profile update or admin-only routes | Elevation | F1, F2 | Role takeover | Permissions derive from a server-side map (`PERMISSIONS` in `apps/api/src/middleware/rbac.ts`); role is re-read from the DB on every authenticated request (the bound query in `requireAuth`, `apps/api/src/middleware/auth.ts`); profile schema has no `role` field (the profile-update schema in `apps/api/src/modules/auth/routes.ts`); farm `organizationId` reparenting is ignored (pinned by `apps/api/tests/booking-and-procurement-scope.test.ts`) | `apps/api/tests/security-matrix.test.ts`; `apps/api/tests/booking-and-procurement-scope.test.ts` | No test asserts every admin route individually; the matrix test samples the boundary |
| AC-06 | Tenant leakage between organizations | Information disclosure | F2 | Cross-tenant farm data exposure | Farms carry `organizationId`; access joins `OrganizationMember` (membership rows in `apps/api/src/modules/organizations/routes.ts`; `assertFarmAccess` in `apps/api/src/modules/farms/routes.ts`) and CORPORATE/COOPERATIVE farm reads are scoped (same file) | `apps/api/tests/tenant-isolation.test.ts` | RLS is not enabled at the database level (OD-05), so a scoping bug in a new query would not be caught by the schema |
| AC-07 | Double payout or double withdrawal from the wallet | Tampering | F2 | Money duplication | Payout transitions `COLLECTED → PAID` as an atomic claim before crediting (`POST /payments/payouts`, `apps/api/src/modules/payments/routes.ts`); withdrawal availability is re-read under the wallet row lock and held in `heldPaisa` (`POST /wallet/withdrawals`, same file); approve/reject are single-claim transitions (`POST /admin/withdrawals/:id/decision`, `apps/api/src/modules/admin/routes.ts`) | `apps/api/tests/concurrency.test.ts`; `apps/api/tests/withdrawal-race.test.ts`; `apps/api/tests/wallet-withdrawals.test.ts` | SQLite has no row locks; the serialisation guarantee is exercised on the PostgreSQL profile (`apps/api/tests/withdrawal-race.test.ts` notes the lock semantics) |
| AC-08 | Forged or replayed payment webhook | Spoofing / Tampering / Repudiation | F4 | Free goods, double side effects | MD5 `verify_sign` recomputed and compared with `timingSafeEqual`, gateway status gate, amount and currency cross-check against the stored payment, and the `PENDING → SUCCEEDED` claim as the single idempotency gate (`apps/api/src/modules/payments/webhook.ts`) | `apps/api/tests/payments-integrity.test.ts`; `apps/api/tests/payments-webhook-amount.test.ts`; `apps/api/tests/payment-confirm-webhook-race.test.ts` | The webhook has no timestamp window; replay of an already-final webhook is a no-op but still accepted, and a superseded intent is left for manual reconciliation (the not-claimable branch, same file) |
| AC-09 | Malicious or oversized upload to `POST /disease/cases` | Tampering / DoS | F1, F3 | Stored malware-like payloads, memory pressure, PII in EXIF | MIME allowlist, 8 MB cap, magic-byte check, raw read ceiling with continued drain, JPEG EXIF strip / malformed-JPEG rejection, and orphan cleanup on insert failure (the upload pipeline in `apps/api/src/modules/disease/routes.ts`) | `apps/api/tests/disease-upload-integrity.test.ts`; `apps/api/tests/disease-upload-rate-limit.test.ts`; `apps/api/tests/security-matrix.test.ts` | PNG/WebP metadata passes through unchanged (documented in the route comment); no malware scanning is performed |
| AC-10 | SSRF through a provider URL | Tampering | F3 | Server-side requests to attacker-chosen hosts | No request URL is derived from user input: outbound calls use env-configured or fixed bases (`apps/api/src/providers/ai/openai-compat.ts`, `apps/api/src/providers/weather/openweather.ts`, `apps/api/src/providers/storage/s3.ts`, `apps/api/src/providers/payment/sslcommerz.ts`) | No dedicated SSRF test exists | An operator setting `OPENAI_BASE_URL`/S3 endpoint to a hostile value is out of application control; discovery endpoints are not used |
| AC-11 | XSS in the SPA or API responses | Tampering | F5, F1 | Session/token theft (ADR-0003) | React escapes rendered content; no `dangerouslySetInnerHTML` in `apps/web/src`; API responses are JSON with `X-Content-Type-Options: nosniff` and a hash-pinned CSP on the SPA (`apps/web` release preflight; live headers in the 2026-10-19 probe set, which is not in this repository — see `docs/STATUS.md` §Where the evidence lives) | `apps/api/tests/security-observability.test.ts` covers API security headers; no dedicated XSS test | Any future raw-HTML sink or dependency injection point is uncovered; CSP mitigates but does not eliminate script execution on the origin |
| AC-12 | CSRF against authenticated endpoints | Spoofing | F1 | Unauthorised state change | The API authenticates with a bearer `Authorization` header only and sets no auth cookie; CORS reflects only configured origins (the `cors` middleware in `apps/api/src/app.ts`, `corsAllowedOrigins`); origin list is production-filtered (`apps/api/src/config/env.ts`) | `apps/api/tests/cors-origin-policy.test.ts`; `apps/api/tests/security-observability.test.ts` | If a future change moves tokens to cookies, this control must be revisited with explicit CSRF defence (OD-02 option b) |
| AC-13 | Rate-limit evasion behind shared NAT or forged proxy headers | DoS | F1 | Endpoint exhaustion | Global limiter on `/api/*` (the `rateLimit` middleware in `apps/api/src/app.ts`); auth-heavy endpoints have their own limiters; financial and checkout limiters key by authenticated user (`apps/api/src/modules/marketplace/routes.ts`, `apps/api/src/modules/payments/routes.ts`); `trust proxy` is explicit (`apps/api/src/app.ts`); Redis store shared when configured (`limiterStore`, same file) | `apps/api/tests/rate-limit-envelope.test.ts`; `apps/api/tests/rate-limit-redis.test.ts`; `apps/api/tests/auth-rate-limit-envelope.test.ts` | With the memory store the effective quota is instances × limit; the fail-open is documented (`docs/security.md`) |
| AC-14 | Secret leakage through logs, metrics, or error bodies | Information disclosure | F1, F2 | Credential and PII exposure | Pino redaction list covers authorization headers, passwords, tokens, phone, coordinates (`apps/api/src/shared/logging/logger.ts`); `/metrics` is token guarded in production and fails closed (`apps/api/src/middleware/metricsGuard.ts`); production startup refuses default/short JWT secrets (the boot gate in `apps/api/src/config/env.ts`); CI runs Gitleaks (`.github/workflows/ci.yml`, `gitleaks` job) | `apps/api/tests/log-redaction.test.ts`; `apps/api/tests/security-observability.test.ts` | Error envelopes carry a `reference` and request id, not messages; a new log field carrying PII would need an explicit redaction path |
| AC-15 | Prompt injection against the AI advisory | Tampering | F7 | Harmful or off-policy farming advice | Questions are sanitised, the model prompt separates user and reference roles, and no tool/action surface is exposed (`apps/api/src/providers/ai/gateway.ts`; `apps/api/src/providers/ai/knowledge.ts`) | `apps/api/tests/ai-prompt-injection.test.ts`; `apps/api/tests/ai-eval.test.ts` (injection neutralisation, out-of-domain refusal) | Answers remain advisory only; low-confidence answers carry an expert-verification note, and KB provenance itself is a separate open item (OD-14) |
| AC-16 | Mass account creation | DoS | F1 | Fake accounts, notification/SMS abuse | Registration limiter 10 per hour per IP (`registerLimiter` + `REGISTER_RATE_LIMIT_MAX`, `apps/api/src/modules/auth/routes.ts`); self-service registration is farmer-only (the register handler pins `role: "FARMER"`, same file) | `apps/api/tests/auth-rate-limit-envelope.test.ts` (limiter envelope class); no registration-specific abuse test exists | Phone verification is the only identity check and is not deliverable in production today (OD-15) |

## Abuse cases without a dedicated test

These controls are implemented but not pinned by an automated test in this repository; they are
the first places to add coverage when the surface changes:

- AC-10 (SSRF): no request URL is user-controlled today, but no test asserts that property.
- AC-11 (XSS): API security headers are tested; the SPA has no automated XSS or DOM-sink test.
- AC-12 (CSRF): covered indirectly by CORS tests; no test asserts "no auth cookie is ever set".
- AC-16 (registration abuse): the limiter class is tested, not the registration-specific policy.
- Password policy beyond length (8-72 chars — the password schema in `apps/api/src/modules/auth/routes.ts`) has no
  strength test.

## Repudiation and audit trail

Every state transition that moves money or authority writes an audit row through
`apps/api/src/middleware/audit.ts`: order checkout/cancel/delete, payment confirm/refund, payout,
procurement review transitions, withdrawal decisions, OTP verification, account deletion, AI
feedback, and admin user/region changes. The admin audit viewer is
`GET /api/v1/admin/audit-logs` (`apps/api/src/modules/admin/routes.ts`). Audit rows are
append-only from the application's perspective; there is no delete path exposed.
